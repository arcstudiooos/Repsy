# Kinetic Sprint 1 Implementation Plan — Clients + Basic Programming

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A coach can invite a client, the client accepts and onboards, and the coach builds a program and assigns it, which generates the client's dated sessions. This is the "coach can onboard and assign" outcome of Sprint 1 (D-009).

**Architecture:** Every new tenant table gets FORCED row-level security through a shared `app_current_org()` function. All request work runs inside `withTenant` via `apiHandler`'s `tenant()`. Domain rules live in `packages/core` (scheduling, assignment, program commit, invites), and route definitions in `apps/web/src/server/routes/*` are mounted by thin `app/api/v1/**/route.ts` files. Programs follow D-001/D-002: immutable workout versions, a program version is a slot map, copy-on-assign, and sessions are generated at assign time with the version locked later.

**Tech Stack:** TypeScript (strict), Next.js 16 App Router (`src/proxy.ts` is the middleware), Better Auth, Prisma 7 + PostgreSQL 16 (RLS), Zod 4, React Hook Form, Tailwind + shadcn/ui, Vitest, Playwright + axe, `date-fns` + `@date-fns/tz`.

**Spec:** `docs/implementation-plan.md` (Sprint 1 tickets S1-1…S1-6, Global Constraints, Target data model) as amended by `docs/decisions.md` (D-001…D-010), plus `docs/sprint-0-followups.md` ("Must land first" and the Sprint 1 sections). Where they conflict, decisions.md wins.

## Global Constraints

- Every read and write is scoped to the actor's active organization and membership; **never trust `organization_id` from the client UI**.
- Every tenant-owned table carries `organization_id`, and parent and child tenant IDs must match.
- Every new table with `organization_id` gets `ENABLE` + `FORCE ROW LEVEL SECURITY` and a policy that uses `app_current_org()` (Task 1.2). The RLS guard test in `packages/db/src/rls.test.ts` must stay green.
- API: prefix `/api/v1`; envelope `{data, meta?, error?}`; errors `{code, message, fieldErrors?, requestId}`; statuses 400/401/403/404/409/422/429/500. A cross-tenant lookup returns **404, not 403**.
- Cursor-based pagination for lists. Indexes on `organization_id`, `client_id`, `due_at`, `created_at` and `status`.
- UTC storage with client-local rendering. Scheduled items also store the intended local calendar date.
- Idempotency keys on invitations and submissions.
- No injury or medical-history fields (D-007). Onboarding collects name, email, timezone, preferred units and basic goals only.
- Analytics and logs never capture names, free text or message bodies.
- A slice is done only with: functionality, loading/error/empty states, responsive UX (375/768/1440), permission checks, tests and docs.
- Definition of done per task: `pnpm lint && pnpm typecheck && pnpm test && pnpm test:e2e` green, plus `pnpm format:check`.
- Pilot numbers:
  - max **30** active clients per coach (`Organization.activeClientLimit`)
  - invite expiry **7 days**, single-use, previous link revoked on resend
  - grace default **24h**, range **0–72h**
- Copy and safety:
  - D-001 assignment confirmation copy is verbatim (Task 1.12).
  - Readiness checkbox copy: "I've confirmed this client is ready to start this program."
  - No medical-clearance claims.
- Process:
  - pin exact versions and don't bypass pnpm's `minimumReleaseAge`
  - no repo-wide `prettier --write .`
  - no `git stash`
  - never touch `_old-scaffold/`
  - commit messages end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`

## Review Focus

1. **Concurrent client creation at the limit.** Two coaches' tabs both create the 30th/31st client at once, and only one succeeds. Test in Task 1.3 (`limit holds under concurrency`).
2. **Search input with LIKE metacharacters and odd Unicode.** `%`, `_` and `\` are matched literally, case-insensitively, and a 500-character query is rejected with 422, not a 500. Test in Task 1.3 (`search escapes wildcards`).
3. **Same invite accepted twice at once.** A double-click or two tabs on the same token produce exactly one client membership and link, and the second request gets `INVITE_USED`. Test in Task 1.5 (`concurrent accept links once`).
4. **Existing user from another org accepts an invite.** A coach who owns org A accepts a client invite from org B. That keeps the same `User.id`, adds a `client` membership in B, and both orgs then require selection or switching. Test in Task 1.6 (`existing owner becomes client of another org`).
5. **DST boundaries in scheduling.** Sessions spanning the 2026-11-01 DST change in `America/New_York` keep 23:59 local due times. A coach in another timezone sees the client's local dates. Test in Task 1.11.
