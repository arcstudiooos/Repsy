# Repsy Sprint 2 Implementation Plan — First End-to-End Loop

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The first complete coaching loop runs end to end. A client sees their next workout in the portal, starts it, logs sets and completes it online, and the coach sees the completion on the dashboard and review list. A coach can also log a workout on a client's behalf. The golden-path E2E proves the loop and stays green from here on (D-009 rule 2).

**Architecture:** Sessions already exist from Sprint 1 (generated at assign time, `workoutVersionId` null until locked). Sprint 2 adds `resolveSessionWorkout` (late resolution through the assignment's current program version, D-002 #5), the session lifecycle (`start` locks the version, D-002 #6), `SetLog` rows upserted on `(session, workout_version_exercise, set_index)` (D-004 #7), and read-only review queries over `WorkoutSession` (no `ReviewFlag` until S4-2). The same `/api/v1/sessions/:id/*` routes serve a client acting on their own session and a coach acting for a client in their org; core decides which, from the actor, never from input. Every new table gets forced RLS through `app_current_org()` and composite tenant FKs.

**Tech Stack:** TypeScript (strict), Next.js 16 App Router (`src/proxy.ts` is the middleware), Better Auth, Prisma 7 + PostgreSQL 16 (RLS), Zod 4, React Hook Form, Tailwind + shadcn/ui, Vitest, Playwright + axe, `@date-fns/tz`.

**Spec:** `docs/implementation-plan.md` (Sprint 2 tickets S2-1…S2-5, Global Constraints, Review Focus, Target data model) as amended by `docs/decisions.md` (D-001…D-010), plus `docs/sprint-1-followups.md` ("Must land first in Sprint 2" and "Sprint 2 specifics") and the still-open items of `docs/sprint-0-followups.md`. Where they conflict, decisions.md wins.

## Global Constraints

- Every read and write is scoped to the actor's active organization and membership; **never trust `organization_id` (or a `clientId`) from the client UI**. A client actor only ever reaches sessions whose `clientId = actor.clientId`. A cross-tenant or other-client lookup returns **404, not 403**.
- Every tenant-owned table carries `organization_id`, with composite `(fk, organization_id)` FKs to its tenant parents. New tables get `ENABLE` + `FORCE ROW LEVEL SECURITY` with the `app_current_org()` policy; the RLS guard test in `packages/db/src/rls.test.ts` must stay green.
- History never changes (D-001, D-002): a locked `workoutVersionId` is written once and never changes; completed and skipped sessions stay as they are; workout versions stay immutable (DB triggers, migration 000014).
- API: prefix `/api/v1`; envelope `{data, meta?, error?}`; errors `{code, message, fieldErrors?, details?, requestId}`; statuses 400/401/403/404/409/422/429/500; CSRF origin check on mutations (already in `apiHandler`).
- Idempotent submissions (Review Focus #2): the same set log, completion or skip sent 3× (retry, double tap) produces exactly one row and one completion.
- Units: weight is stored in kg as `Decimal(7,3)`, displayed in the viewer's preferred units at 1 dp, converted only at the edge (`toDisplay`/`fromDisplay`) (Review Focus #5).
- UTC storage with client-local rendering. Session dates shown are the stored `scheduledLocalDate` (the client's calendar date), for the client and the coach alike (Review Focus #1).
- Copy: workout-screen status words are **"Syncing"** and **"Synced"** (D-004 #6). Sprint 2 is online only, so it never claims **"Saved on device"** (that arrives with the IndexedDB outbox in S3-3). Coach-logged sessions show **"Logged by coach"** (D-008 #7). The portal safety reminder is verbatim: "Tell your coach about anything that affects safe training before you begin." (D-007 #5). No medical-clearance claims. Review copy never says "At risk".
- Validation (PRD §9.1 / S2-2): `0 ≤ reps ≤ 1000`, `0 ≤ weightKg ≤ 2000`, `1 ≤ rpe ≤ 10`; the exercise must belong to the session's locked version.
- Workout logging never depends on the worker (D-005 rule 4): every Sprint 2 write goes straight to the web API and Postgres.
- A slice is done only with: functionality, loading/error/empty states, responsive UX (375/768/1440, no horizontal overflow), 44px tap targets on the workout screen, permission checks, tests and docs.
- Definition of done per task: `pnpm lint && pnpm typecheck && pnpm format:check && pnpm test && pnpm test:e2e` green (axe checks on touched screens).
- Process:
  - pin exact versions and don't bypass pnpm's `minimumReleaseAge`
  - no repo-wide `prettier --write .`; no `git stash`; never touch `_old-scaffold/`
  - one writer on `schema.prisma` at a time (tasks are sequential)
  - commit messages end with the Co-Authored-By trailer from the session instructions

## Review Focus

1. **Replay and duplicate submission (Review Focus #2).** The same set-log batch, `complete` and `skip` sent 3× give one row per set and one completion; concurrent `start` calls lock one version. Test in Task 2.5 (`same payload x3`, `concurrent start locks once`).
2. **Units round-trip (Review Focus #5).** 135 lb is stored as kg; it re-displays as 135 lb for the client and 61.2 kg for a coach in kg. Test in Task 2.5 (`units round-trip`) and in the Task 2.6 E2E.
3. **Guessed IDs and dual roles (Review Focus #3).** A client of org B can't start, log or read a session of org A (404); a client can't reach another client's session in the same org (404); `workoutVersionExerciseId` from another version or org is a 422 (never a write). Test in Tasks 2.5 and 2.7.
4. **Late resolution vs locking (D-002 #5/#6).** An unstarted session shows the newly committed version; once started it keeps the locked version after a new commit. Test in Task 2.3 (`unstarted reflects new version`, `locked keeps version`).
5. **Tenant isolation of the review list.** Another org's completions never appear on the dashboard or review list. Test in Task 2.8.

**Interfaces:**

- `type SessionSummary = { id; clientId; scheduledLocalDate: string; dueAt: string; state: SessionState; title: string; exerciseCount: number; loggedByCoach: boolean; startedAt: string | null; completedAt: string | null; overdue: boolean }` (`overdue` = `scheduled` or `in_progress` with `dueAt < now`).
- `listSessions(tx, actor, { clientId?: string; scope: 'upcoming' | 'past'; cursor?: string }, { now? }): Promise<{ items: SessionSummary[]; nextCursor: string | null }>`:
  - client actor: `clientId` input is ignored and replaced by `actor.clientId`; coach: `clientId` required and must exist in the org (else `NOT_FOUND`).
  - `upcoming` = `scheduled` + `in_progress`, ordered `dueAt asc, id asc`; `past` = `completed`, `skipped`, `missed`, `incomplete`, ordered `dueAt desc, id desc`. `cancelled` is never listed. **No filter on `assignment.status`** (an ended assignment keeps its pre-replacement scheduled sessions, D-010 #2).
  - Page size 25, keyset cursor over `(dueAt, id)` (`encodeSessionCursor`/`decodeSessionCursor`, invalid → `VALIDATION`).
  - Titles resolve per row (locked version, else current slot), batched: one query for the assignments' current version slots, one for locked versions.
- `getPortalHome(tx, actor, { now? }): Promise<{ nextWorkout: SessionSummary | null; week: { completed: number; total: number; startLocalDate: string; endLocalDate: string }; showSafetyReminder: boolean; hasAssignment: boolean }>` (client actor only, else `FORBIDDEN`):
  - `nextWorkout`: the earliest `in_progress` session if any; otherwise the earliest `scheduled` session with `dueAt ≥ now`.
  - `week`: ISO week (Mon–Sun) containing today in the client's timezone; `total` = non-cancelled sessions with `scheduledLocalDate` in that week, `completed` = those `completed`.
  - `showSafetyReminder`: true while the client has no session that was ever started, completed or skipped (before their first program starts, D-007 #5).
  - `hasAssignment`: any assignment exists (active or ended).
- `getAssignmentSummary.nextSession` (follow-up): an `in_progress` session of the active assignment wins even when overdue; otherwise the earliest `scheduled`/`in_progress` with `dueAt ≥ now`.

- `startSession(tx, actor, sessionId, { now?, requestId? }): Promise<SessionDetail>` (`session:log`):
  - Locks the session row first (no-op `updateMany`), then re-reads it. Client actor: must be own session (`clientId`), else `NOT_FOUND`.
  - `scheduled` → writes `workoutVersionId` (resolved slot of the current version), `state in_progress`, `startedAt now`. **Idempotent:** an `in_progress` session returns its detail unchanged (double tap; concurrent starts lock once). `completed`/`skipped`/`missed`/`incomplete`/`cancelled` → `SESSION_FINISHED`.
  - Audits `session.started`.
- `upsertSetLogs(tx, actor, sessionId, items, { now?, requestId? }): Promise<SetLogAck[]>` (`session:log`):
  - Session must be `in_progress` (`scheduled` → `SESSION_NOT_STARTED`; finished → `SESSION_FINISHED`). Locks the session row, so concurrent batches serialize.
  - Every `workoutVersionExerciseId` must belong to the session's **locked** version, else `VALIDATION` with fieldError `items` ("This exercise isn't part of this workout."); nothing is written for that batch.
  - Upsert on the unique key. A write whose `clientUpdatedAt` is **older** than the stored one is ignored (`status: 'stale'`, value unchanged); equal timestamp + same `clientMutationId` is a no-op (`'saved'`); otherwise the row is updated.
  - `type SetLogAck = { workoutVersionExerciseId; setIndex; clientMutationId; status: 'saved' | 'stale'; value: SetLogValue }` where `SetLogValue = { reps, weightKg, rpe, durationSeconds, distanceM, clientUpdatedAt }` (numbers, not Decimals).
  - No audit per set (volume); the session's audit trail is start/complete/skip.
- `completeSession(tx, actor, sessionId, { idempotencyKey, comment? }, { now?, requestId? })` and `skipSession(...)` (`session:log`):
  - Lock the row. If `workoutVersionId` is null (completing or skipping without starting), lock it now (D-002 #6).
  - Complete: from `scheduled` or `in_progress` → `completed`, `completedAt = submittedAt = now`, `comment`. Skip: from `scheduled` or `in_progress` → `skipped`, `submittedAt = now`, `comment`.
  - **Idempotent replay:** the same action on a session already in that terminal state returns the stored detail, writes nothing and audits nothing. The other terminal action (skip after complete, or complete after skip) → `SESSION_FINISHED`. `missed`/`incomplete`/`cancelled` → `SESSION_FINISHED`.
  - Audits `session.completed` / `session.skipped` with `{ idempotencyKey, setCount }` (no comment text).
- `getSessionDetail(tx, actor, sessionId, { now? }): Promise<SessionDetail>` (`session:read`): `{ session: SessionSummary & { comment: string | null; workoutVersionId: string | null }, workout: WorkoutVersionView, logs: SetLogValue & { workoutVersionExerciseId; setIndex }[], previous: Record<exerciseId, { localDate: string; sets: { setIndex; reps; weightKg; rpe; durationSeconds; distanceM }[] }>, client: { id; name; preferredUnits } }`. `previous` = per exercise, the set logs from this client's most recent **completed** session (other than this one) that logged that exercise.
- API (all `can: 'session:log'` except GET, which is `session:read`; per-user rate limit 120/min on `logs`):
  - `GET /api/v1/sessions/:id` → `SessionDetail`
  - `POST /api/v1/sessions/:id/start` → `SessionDetail`
  - `POST /api/v1/sessions/:id/logs` body `{ items }` → `{ data: SetLogAck[] }`
  - `POST /api/v1/sessions/:id/complete` and `/skip` body `{ idempotencyKey, comment? }` → `SessionDetail`
- Units (Review Focus #5): `fromDisplay(135, 'lb') = 61.235`, `toDisplay(61.235, 'lb') = 135`, `toDisplay(61.235, 'kg') = 61.2`. Stored as `Decimal(7,3)`, read back as `61.235`.
